# Caching of Candidate Data
                           
Candidate data is spread across multiple tables in the database.
Making all those joins can lead to performance issues.

To improve candidate fetch performance, we make use of a Redis cache and a special 
caching table (`candidate_json_cache`). Those caches store all the data for a candidate in a 
single JSON object, together with a version number which is used to detect stale data.

This allows us to fetch all candidate data for a given candidate with a single cache query 
or a single database query with no joins. 

## Architecture
                                                           
`CandidateDtoFetchService` - is the entry point for this architecture. 
It is responsible for fetching the complete data for one or more candidates by their ids. 

Changes to candidate-related data are detected using database triggers. 
These can be found in Flyway starting with `V1_398__add_cached_json_support.sql`.
That Flyway sets up a trigger on each table called `<table name>_bump_version` which updates
the `candidate` field `data_version`.

Cached data (in Redis or in the `candidate_json_cache` table) is considered stale if its version 
does not match the current `data_version` of the candidate.

You can see the key processing code in the implementation of `CandidateDtoFetchService.fetchByIds`.

In that code you will see that if a current JSON representation of a candidate's data is not found 
in the Redis or table cache, then a new JSON representation is generated by 
fetching all the data from the database. 

This is performed by `CandidateJsonDao.loadJsonByIds`, which in turn calls 
`SqlJsonQueryBuilder.buildJsonQuery` which builds an SQL query that constructs a JSON
representation of the candidate data by joining all the relevant tables and using the 
`json_build_object` function to create a JSON object. 
It is guided by annotations on the `xxxReadDto` classes, such as `@SqlColumn` and `@JsonOneToMany`
(see the code for these in the `annotation` subdirectory).
Then that JSON object is stored in the caches, deserialized from JSON into a `CandidateDto` object 
and returned to the caller.

I have described the process for a single candidate id – but in fact multiple candidates can be
fetched in a single call to `CandidateDtoFetchService.fetchByIds`. Some will come from Redis, 
some will come from the table cache, and some will have to be fetched from the various 
candidate-related tables.
